# Integração iFood MVP — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir que uma empresa conecte uma loja iFood, opere todos os pedidos normais no ZeloPDV e materialize, ao receber `CONCLUDED`, uma venda bruta idempotente fora do caixa, visível nos relatórios e compreendida pelo Zelinho.

**Architecture:** Um endpoint SvelteKit valida e persiste webhooks; um worker Node sempre ativo no Dokploy processa inbox, polling, comandos e presença por merchant. O módulo profundo `IfoodIntegration` traduz o protocolo externo para `zelo_orders`; Supabase mantém inbox/outbox, leases e identidades idempotentes; Pedidos, Cozinha, relatórios e Zelinho consomem apenas contratos internos.

**Tech Stack:** SvelteKit 2, Svelte 5, Node.js 24, Supabase/PostgreSQL, Vitest, Playwright e Docker/Dokploy.

**Spec:** `docs/superpowers/specs/2026-09-15-ifood-mvp-design.md`

**ADR:** `docs/adr/0001-ifood-worker-dedicado.md`

## Contrato de documento vivo

Este arquivo é o tracker canônico da implementação e **deve ser alterado em todo commit das Tasks 1–21**.

Antes de concluir cada task, o executor deve:

1. marcar todos os seus checkboxes;
2. trocar o status da linha correspondente para `Concluída` ou `Bloqueada`;
3. preencher o bloco `Resultado real` da task com data, comandos executados, contagens e desvios;
4. atualizar `docs/CURRENT.md` com o estado verificável da integração;
5. incluir este plano e `docs/CURRENT.md` no mesmo commit da implementação.

O SHA do próprio commit não é gravado dentro dele, pois isso criaria uma referência recursiva que muda a cada amend. O assunto de commit da tabela é a identidade estável. O SHA é resolvido com:

```powershell
git log --fixed-strings --grep "<assunto exato>" --format="%H %s"
```

Uma task nunca é considerada concluída apenas porque o código foi escrito. O teste RED deve falhar pelo motivo esperado; o teste GREEN deve passar; o diff deve estar limpo de placeholders e `git diff --check` deve passar. Se houver falha conhecida, a task fica `Bloqueada` e o commit registra somente evidência recuperável — nunca código parcialmente habilitado.

## Restrições globais

- Usar TDD: RED, implementação mínima, GREEN, refatoração.
- Gerar toda migration com `supabase migration new <nome>`; nunca inventar ou renomear timestamp manualmente.
- Não aplicar migration no projeto vinculado nem publicar imagem/branch sem autorização explícita do dono.
- Tabelas de integração ficam em `ifood_internal`, sem grants para `anon` ou `authenticated`.
- RPCs públicas que atravessam o schema privado são `SECURITY DEFINER`, fixam `search_path`, detectam service role pelo contrato vigente, revogam `PUBLIC` e concedem somente o mínimo.
- Browser nunca recebe `clientSecret`, access token, payload bruto ou credencial privilegiada.
- Logs e testes não contêm telefone, endereço, CPF, Authorization ou segredo real.
- `event_id`, pedido externo, comando, compromisso de estoque, impressão, venda e estorno têm chaves idempotentes independentes.
- Um HTTP `202` de comando iFood não muda o estado comercial; apenas evento externo confirmado muda `zelo_orders.status`.
- Toda venda iFood usa `id_caixa = null`, inclusive quando a forma declarada é dinheiro.
- Item não mapeado não bloqueia o pedido e não movimenta estoque.
- O cardápio, Financial, repasses, clientes/Pessoas, aceite automático e backfill histórico permanecem fora do MVP.
- A badge inicial é textual. O logotipo oficial só entra após autorização formal documentada.
- O alerta sonoro genérico do ZeloPDV é outro plano; aqui ele aparece somente como gate de rollout.
- Ao tocar superfícies críticas, reler os documentos exigidos por `AGENTS.md` antes da edição.
